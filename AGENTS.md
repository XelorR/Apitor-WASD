# Apitor-WASD

Single-file Python CLI remote for Apitor robots (R, J, S, Q, X, Wheels) over Bluetooth LE via the `apitor-ble` library. The whole app is one module, `apitor_remote.py` (~3700 lines). The regression suite is hand-rolled plain Python in `tests/` (no pytest, no CI, no packages, no lint/typecheck/format config — do not look for `ruff`, `mypy`, or a `pyproject.toml`). License: GPL-3.0 (see `LICENSE`).

## Commands

- Install: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt` (Python 3.10+; only dependency: `apitor-ble>=0.3.0`)
- Double-click launchers: `run.sh` / `run.bat` do the same as Install+Run in one file (create `.venv`, install `apitor-ble` when missing, then `exec` the app with the same flags). `run.sh` is executable in git, uses bash builtins only (`${0%/*}` instead of `dirname`), and re-opens a terminal emulator (foot, kitty, gnome-terminal, …) when started without a TTY from a graphical session; `APITOR_NO_TERM=1` suppresses that, `PYTHON=…` picks the interpreter. `run.bat` is ASCII + CRLF on purpose (cmd.exe codepage).
- Run: `.venv/bin/python apitor_remote.py` — full-screen TUI by default; requires a real terminal (exits 2 if stdin is not a TTY). `--no-tui` switches to the old plain line-by-line output; `--tui` is still accepted as a hidden compatibility alias.
- Without a robot: `.venv/bin/python apitor_remote.py --simulate` — prints BLE command frames to stdout instead of connecting (use this to verify changes)
- Run a program file: `.venv/bin/python apitor_remote.py --program examples/квадрат.txt` (`examples/square.txt` is the English version)
- Tests: `.venv/bin/python tests/run_tests.py` (all `tests/test_*.py` in parallel, `--jobs 1` sequential, `-k NAME` filter, `--list` to enumerate; README «Тесты»). Each suite is a standalone script (plain PTY/subprocess, no pytest) runnable on its own; `tests/harness.py` gives `ROOT`/`PY`/`APP`/`NOKS`/`fresh_work()` and points `HOME` at a throwaway temp dir, so the real `~/.config`, `programs/` and `/dev/input` are never touched. Keep the suites (and `tests/test_apitor22.py`'s docs-sync check) in sync when hotkeys, flags or wording change.
- Build the printable kids' manual: `docs/build.sh` (needs `pandoc`, `graphviz`, `calibre`; markdown + `docs/diagrams/*.dot` → `docs/img/*.svg` + `docs/instructions-{ru,en}.pdf`)
- Exit codes: `0` clean quit, `2` error (bad profile, unreadable program file, no TTY), `130` Ctrl+C

## Gotchas

- Drive modes are user-facing names: `j` = hold (the robot drives while the key is
  held), `k` = **cruise control** (drives on until `пробел`/another direction — the
  internal state is still `latched`, the flag is `--cruise` with a hidden `--latched`
  alias, the TUI status says `круиз-контроль`/`cruise`). The run journal has **no
  hotkey**: only `--log`/`--no-log`/`config.journal` (`_toggle_journal` is gone, `l`
  is unassigned).
- Key-state (reading real key press/release from `/dev/input/event*`) is always attempted on Linux and is the default hold behavior; it needs the `input` group (`sudo usermod -aG input "$USER"`, then re-log) or root, otherwise the app warns and falls back to auto-stop by `--hold-timeout`. `sudo` works but is not recommended: it creates root-owned state files in `~/.config/apitor-control/`. `--no-key-state` turns the tracking off entirely (no `/dev/input` access at all, no warning). `--key-state-device` restricts which devices are watched, and holding Shift boosts the speed to 12 in remote mode only (restored on release). On Windows the same tracking goes through WinAPI (`GetAsyncKeyState`, class `WinApiKeyState`): no rights needed, and it accepts a `user32` stub for tests (`tests/test_apitor23.py`) — scan code → VK must be asked with `MAPVK_VSC_TO_VK_EX` (=**3**; 2 is `MAPVK_VK_TO_CHAR`, which reads the D scancode 0x20 as VK_SPACE and made `d` stop turning the robot right — a real bug fixed that way), and each action listens to the layout VK, the Latin VK and its arrow at once.
- State lives in `~/.config/apitor-control/`: `addresses.json` (one cached Bluetooth address per model), `config.json` (lang, timings, journal), `runs.log`. Program files and the `_draft.txt` autosave live in `programs/` next to the script (overridable with `--program-dir` or `program_dir` in config). Flag priority: CLI flag → `config.json` → default.
- With a cached address, `q` connects directly without scanning; `--no-cache` disables this. If the cached robot is off, the app falls back to scanning and updates the cache.
- Robot drive directions are unverified on hardware for Robot R — after connecting, press `y` (test drive) and use `--flip-left/--flip-right` or `--left-motor/--right-motor` if directions are wrong.
- `Ctrl+C` stops all motors and disconnects before exiting.
- The TUI is the default and draws a full-screen dashboard on the alternate screen with raw ANSI codes — no external deps: a permanent banner (status line + `Tui._mode_banner`, the mode name and its keys, wrapped by `_wrap_words` over `BANNER_ROWS`), and, only while a prompt is open, the input bar (`Tui._prompt_line`). The remote mode has its own layout (`Tui._render_remote`, used when `mode == "remote"` and not recording): under the banner, `_remote_program_block` draws the **last program frame** (title `последняя программа` + the loaded file name, `(пусто) · Enter нечего запускать` when empty) — this is exactly what `Enter` will run; then `_wasd_art` centers four boxes in an inverted-T (`W` above `A S D`, each with its letter and arrow) using the largest that fits (15×7 → 13×5 → 9×3 → one-line `W↑ A← S↓ D→`); then `_log_block` draws the log in its own frame at the bottom (3..8 rows, last lines only). The editor/once modes keep the old bottom **program frame** (`Tui._program_block`: a 3-row box with the title `программа`/`разовая программа · N шагов · ~T с · скор. N`, the steps and a trailing `▏`, `(пусто)` for an empty program); run/recording keep the old single `[prog]`/`[rec]` row. On a very short terminal the editor frame falls back to the single line and the remote layout falls back to the compact old one. The live editor line is not copied into the log (the frame is the source of truth); `_say`/`note` still log the mode entry, load/save and hints, but the startup keys hint is deliberately not logged in the TUI (the banner already shows those keys, and the five-line log frame must leave room for the key-state warning). All output goes through `Remote._emit`/`_say` (tag-aware: `Tui.note(tag, text)`), prompts render in the bottom bar from `self.prompt` (`title`/`text` keys), the external `$EDITOR` pauses (leaves the alt screen) and resumes the TUI, and `SIGWINCH` triggers a redraw. Non-TUI output (`--no-tui`) must stay byte-identical to the old plain prints.
- Program files are plain text: RU and EN words both accepted (`вперёд` = `forward`/`up`, `назад` = `back`/`down`, `right` also as `rght`), single-symbol shorthand shown in the editor row is also parsed (`↑` `↓` `←` `→` `‖` `✦` `●3` `»8`, e.g. `↑5 →2`), `#` comments, `e`/`ё` and case forgiven, `×`/`*`/`,` as separators.
- Timed steps (`Step.seconds`) are the macro format: a number with a unit — `вперёд 1.2с` / `1.2s` / `1.2сек` / `1.2sec` / `1.2 seconds` (both `с` and `s` parse in either UI language; the language only decides what is written) or a bare `1.2` — means "drive for 1.2 s" instead of "1.2 steps". Counts and seconds mix freely in one file; `скорость N` is the program header only before the first step, mid-file it is a `»N` step ("change speed from here"). Durations round to 3 decimals (1 ms) — `secs_text`/`STEP_PRECISION`; the run loop `_run_motion`/`_sleep_checked` sleep against an absolute deadline (`RUN_TICK = 0.02`) so long macros do not accumulate drift. `MIN_STEP_SECONDS = 0.05`, `MAX_STEP_SECONDS = 600`; blink/color/repeat/speed cannot take seconds.
- Macros: `Remote._start_recording` (`m` only starts the recording; `Esc` and `n` stop it, and `m` while recording just says so) drives `MacroRecorder` (in `apitor_remote.py` after `parse_program`), which is fed from `_on_move`/`_stop` (movement segments), `_set_led`/`_led_blink` (`_rec_event`) and `_apply_speed_if_moving` (boost splits a segment into `»12 … »6`). Pauses become `pause` steps (`MIN_ACTION = 0.05`, `MIN_WAIT = 0.1`; a trailing pause before the stop is dropped), speed changes while idle are emitted just before the next motion. The finished macro is loaded into the editor as the "last program" (`set_program(...)`, `program_name = None`, `_draft_loaded = True`), so `Enter`/`r`/`t`/`f`/`g`/`p`/`x` work on it unchanged; while recording, `p`/`o`/`Enter`/`r`/`t`/`x`/`f`/`g`/`i`/`e` are blocked with `идёт запись макроса — сначала Esc или n (стоп)` (`_handle_action` checks `self.recording`, and `_start_program_run` guards the editor's `Enter` too).
- Reverse runs: `Enter` executes the program everywhere (remote included), `Shift+Enter` runs it without pauses (key-state Shift, or the terminal's own `s-enter`). `r`/`R` (`rev_back`/`rev_back_np`) drive the route back **backwards** (forward<->back and left<->right mirrored), `t`/`T` (`rev_front`/`rev_front_np`) for a robot turned around by hand (only left<->right). `reversed_steps(editor, mode, drop_pauses=..., base_light=...)` builds the program on the fly (`REVERSE_MIRROR` maps the kinds; count steps become seconds; the editor program is left untouched; repeat is forced to 1 because a second pass starts from a different heading). Colours and speeds are emitted at their **change points**, not before every step: the effective speed/light of each step is tracked (header speed = `editor.speed`, light starts at `base_light`) and `»N`/`●c` are emitted only when the value differs from what is already set — so `скорость 6 … скорость 12 …` comes back as `»12 … »6 …` (the run starts at the speed of the route's end and switches back at the breakpoint), and `●c` stands exactly where a colour stretch begins in the reversed route. `base_light` is the LED number that is on before the run (`_start_program_run` passes `NUMBER_BY_COLOR.get(self.led_color)`), so stretches driven "with whatever was lit" get that colour back; `None` means unknown and those stretches are left alone. Blinks stay blinks, `pause` steps are kept unless dropped. `RunPlan` carries steps/speed/repeat/rev/drop_pauses plus `editor`/`source` (`"editor"` or `"once"`) from `_start_program_run` to `_run_worker`, which prints `реверс задним ходом` / `реверс передом (робот развёрнут)` / `без пауз` (and ` · разово` for a one-time program) in the start line.
- Partial reverse: pause a run (`пробел`) and press `r`/`t` (or `R`/`T`) — the robot drives back **only what it has already driven**, a quick way to bring it home after a wrong turn. `_run_worker` keeps `_run_done` (fully driven steps), `_run_current` + `_run_progress` (the step in flight and its driven seconds, updated in `_run_motion`/`_sleep_checked`) and `_run_led` (the LED the run has set); `partial_reverse_steps(done, editor, mode, *, current, used, drop_pauses, base_light)` turns the in-flight motion into a timed mirrored step (only if `used >= MIN_STEP_SECONDS`, clamped by the step's own duration; pause/blink/colour/speed in flight are dropped, completed ones keep the usual reverse rules) and reuses `reversed_steps(..., steps=...)`. `_partial_reverse` builds the plan from `_run_editor`/`_run_source` (so a one-time run reverses its own editor), sets `_run_abort = "partial"` and `_partial_pending = True` (the worker prints `пауза на шаге N из M — везу обратно по проеханному` and journals `пауза на шаге N/M`), then **does not block the key handler**: `_finish_partial` awaits the old task in the background (3 s safety timeout, connection check) and calls `_launch_run(RunPlan(..., partial=True))` — `_launch_run` is the shared "start a ready plan" helper `_start_program_run` uses too and clears `_partial_pending`. `Esc`/`p` during the wait cancel the pending handoff. The start line becomes `реверс проеханной части (задним ходом)` / `(робот развёрнут)`; without a pause `r`/`t` during a run only print a hint. The editor program is left untouched. `_sleep_checked` freezes its deadline while paused (the old code shrank the remaining time every tick and a pause step could end by itself); `_run_motion` likewise freezes the in-flight `_run_progress`.
- Partial resume (Enter on pause): `RunPlan.origin` carries a `ResumeInfo` snapshot of the program the run reverses: copied `steps`, 0-based `index`, `used` seconds of the current step, `editor`/`source`, the run's `speed`/`led` at the pause, and `repeat`/`rep` (the cycle being driven). `_start_program_run` sets it for a full reverse with `index=len(steps), used=0` (nothing left after the route); `_partial_reverse` sets it from `_resume_info_from_run()` (the plan being reversed, not the editor), so a reverse of a reverse resumes the right route; `_run_worker` keeps `_run_rep` for the current cycle. `ResumeInfo.remaining()` returns the rest of the current movement step (or pause) of **this** cycle, drops a started blink/colour/speed step, appends everything after it, and `merge_moves` glues adjacent same-kind timed moves (`↑16с + ↑4с → ↑20с`); `remaining_all()` also appends the full remaining cycles (`repeat - rep`) for a repeated program. `_resume_plan(drop_pauses=False)`: for a normal run it calls `remaining_all()`; for a reverse it runs `reversed_steps(editor, plan.rev, steps=_run_done + partial current)` to undo exactly the reverse prefix, appends `plan.origin.remaining_all()`, restores the original speed/colour at the boundary via `route_end_state`, and merges moves. The result is `RunPlan(..., rev=None, repeat=1, partial=True)`, so the start line says `продолжение с места`. `_partial_resume` (plain `Enter` in `_handle_run_key`, `Shift+Enter`/`s-enter` in `_handle_key`) sets `_run_abort="resume"` + `_partial_pending`, stops the old run through the same `_finish_partial`, and the worker prints `пауза на шаге N из M — продолжаю с места` / journals `продолжение с шага N/M`. Plain `space` during the handoff cancels both `partial` and `resume`; one-time cleanup is skipped for both. The exact example from the report: route `↑5с →5с ↑20с`, pause at 16 s, `r` (back 16 s), pause 3 s into the left turn, `Enter` → `→3с ↑20с` (undo right 3 s + 16 s forward + the remaining 4 s, merged).
- One-time program: `o` (`once_prog`) opens `self.once_editor` — a separate `ProgramEditor`, never saved (`f` and `e` are refused; the `_draft.txt` autosave and the "last program" `program_name`/`self.editor` stay untouched) and cleared after its run (including an aborted one), unless a partial reverse/resume is still using it. `Enter`/`Shift+Enter` and `r`/`t` run it via `RunPlan(source="once")`; `g` loads into it (`_open_load_prompt(target="once")`), `x` clears only it, `p` goes to the usual editor, `Esc`/`o` back to the remote (it stays until run). After a once run, `Enter`/`r`/`t` use the `p` program again; the journal records it as `(разово)`.
- Key map: `Enter` = `run` (executes; warns when the program is empty; on a paused run it resumes with `_partial_resume`), `esc` = stop (and ends a macro recording, like `n` — `m` only starts it), `r`/`R`/`t`/`T` = reverse runs, `o` = one-time program (a separate editor, not saved, gone after one run), `y` = test drive (moved off `t`), `e`/`E` = external editor (`$EDITOR`) in **both** modes (`edit_external`), `v`/`V` = motor 3 (moved off `e`). The reverse keys `r`/`R`/`t`/`T` are `rev_back`/`rev_back_np`/`rev_front`/`rev_front_np` and work in **both** the remote and the editor (`_handle_action` only blocks `test`/`identify`/`m3_*`/`hold`/`latch`/`blink_led` there); the editor's own repeat moved to `*` (`ProgramEditor.key`, `_arm("repeat")`) so that `r` could be the route back. `_to_latin_layout` maps the Russian layout for all of it (`к`->r, `е`->t, `н`->y, `т`->n); `{`/`}` (Shift+brackets on a US layout) and the Ukrainian `ї`/`Ї` also become `[`/`]`, so the speed keys survive a held Shift or a non-Russian Cyrillic layout.
- The editor's speed keys must always answer visibly: `ProgramEditor.line()` puts the speed into the **empty** program line too (`(пусто) · скор. 6 …`), `Tui._program_line` shows that line in the editor even with no steps, and at the limit `_speed` returns a `warn` («скорость уже 12 (предел 1..12)») while still arming the `]12` digit capture — otherwise `]`/`[` on an empty program or at speed 12 look dead (a real "не работает" report).
- `Shift+Enter` = run without pauses (`drop_pauses`). Shift comes from key-state (`_shift_held()`) when it works, otherwise from the terminal itself: `RawTerminal.__enter__` calls `_enable_key_protocol(fd)`, which asks the terminal with the kitty keyboard protocol query (only capable terminals answer), pushes the disambiguate flag on a reply and pops it on exit — and also around the external editor (`_key_protocol_off`/`_key_protocol_on`). `_decode_csi` then turns `CSI 13;2u` and xterm's `CSI 27;2;13~` into the `s-enter` token (Ctrl+letter into its control char, Shift+letter into uppercase, release events `:3` are ignored). Shift-*letters* (`R`, `T`) never needed key-state — the terminal sends the uppercase char itself.
- Program colour steps use `COLOR_BY_NUMBER`/`NUMBER_BY_COLOR` (0..8 ↔ `Color` enum): `цвет 8` is white and `Color.WHITE == 10`, so never pass the file number straight into `Color(...)`.
- `docs/` is the printable RU/EN kids' manual: `instructions-*.md` + `diagrams/*.dot` + `style.css`, built by `docs/build.sh` (pandoc → HTML → calibre `ebook-convert` PDF with `--paper-size a4`, `--pdf-default-font-size 13` / `--pdf-mono-font-size 11` — the base font size lives here, not only in the CSS — `--page-breaks-before="//*[name()='h1']"` — one page per chapter — and footer numbers via `--pdf-footer-template`). Generated `img/*.svg` and the PDFs are committed; `docs/*.html` is gitignored. No emoji in the text (no font coverage in PDF): use the program symbols `↑ ↓ ← → ‖ ✦ ● »` and `★` instead. The RU and EN versions are kept in sync: same chapters, same page map (`instructions-*.pages.json`), same tables/missions; keep an eye on the fill of each page (`pdftoppm` + a quick scan for the last non-white row) so no page is left half-empty.
